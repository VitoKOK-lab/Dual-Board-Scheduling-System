# 設計取捨與待確認事項

## 1. Plan Y 預備隊本身也會被排入點位（待主管確認）

**現況**：預備隊是「本週負擔最輕的 2~3 人」，但他們仍然照常被排進白板點位。

**原因**：種子配置下，早修 24 個名額 + 午休 23 個名額 × 5 天 = 235 人次，除以 36 人約每人每週 6.5 次。
在這個人力密度下**沒有人是空閒的**，「預備隊」只能是相對負擔最輕，不可能是完全沒排班。

**影響**：臨時缺人時，Plan X 面板中預備隊成員經常帶著「當日同時段已有點位」的衝突標記，
反而排在真正當天有空的人後面。目前的排序（無衝突優先）會推薦真的補得上的人，實務上更可用。

**另一個選項**：把預備隊人員從白板矩陣中完全抽離，讓他們整週真的待命。
代價是其餘 33 人的每日負擔上升約 9%，且預備隊那週等於放假。

**需要主管決定**：預備隊要「相對最輕」還是「真的空著」。程式改動集中在
`src/domain/scheduler.js` 的步驟 E——若要抽離，需改為先選預備隊再排白板。

---

## 2. 重新排班會覆蓋手動調整

「一鍵自動排班」整批重建該週明細，包含所有 `is_override` 的手動調整。前端已加確認面板，
但沒有還原機制。若需要「只重排未手動調整的名額」，需另立 API 與保留策略。

---

## 3. 黑板全週職務者不接每日職務屬軟性限制

交接／值日生持有者預設不再接餐車／升旗／午休回來，但人力不足時會自動放寬並回報
`CONSTRAINT_RELAXED`。若這在實務上不可接受，應改為硬性限制並讓名額留空。

---

## 4. 公差的兩種效果

規格 §2.2 只說公差「不影響公平性計數」。本實作額外讓**已登錄的公差在自動排班時避開該人當日**——
這是「已知公差登錄」按鈕放在排班之前的必然含義。若主管希望公差只做提示、仍照排，
需移除 `src/domain/scheduler.js` 中的 `applyAbsences` 過濾。

---

## 5. 早修與午休「點位不重複」以點位名稱判定

白板早修與午休是兩組獨立的 `location_tasks` 列，但同名點位（如「育英樓」）視為同一地點。
因此限制條件實作為「同一人當日的午休點位名稱 ≠ 早修點位名稱」，而非比對 `item_id`。
